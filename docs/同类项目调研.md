# 同类项目调研（开源 / GitHub）

> 目的：看看别人怎么做「从 MIDI 提取调性与和弦」，哪些设计可以照抄，哪些坑他们已经踩过。
> 调研方式：GitHub 搜关键词 + 逐个读 README 与设计文档（`libcantus` 的 `docs/en/analysis.md` 读得最细）。
> 前置：[Loop 和声提取可行性分析](./Loop和声提取可行性分析.md)

---

## 0. 结论先说

1. **最接近我们目标的项目是 `libcantus`**，而且它的思路和我们第二版（全局解码）高度重合，只是**更完整**：
   分段是"搜"出来的不是切出来的、置信度有明确定义、有"简化"机制过滤经过和弦、增六单独处理、终止式分六类。
2. **没有一个开源项目专门做"采样包 loop"的和弦提取**。现成项目要么面对完整乐谱，要么面对实时键盘输入，要么面对音频。
   我们这个场景（短、循环、常缺声部、文件名带调性、常常没有速度事件）是空白。
3. **可以直接抄的有 5 条**，其中"增六看解决方向"正好补上我们已知的缺口。

## 一、libcantus —— 最相关，几乎是同类

| 项 | 内容 |
| --- | --- |
| 地址 | [libraz/libcantus](https://github.com/libraz/libcantus) |
| 技术形态 | 纯 TypeScript 参考实现（零依赖、可摇树）+ C++17 核心，另提供 WASM / Node / Python / 命令行 |
| 许可 | Apache-2.0 |
| 能力 | 从音符事件里认和弦、判调性、出罗马数字、认终止式、找转调、判断曲式；反过来还能"照着这个和声写新声部" |
| 明确不做 | 不读写 MIDI 文件（"bring your own parser"）、不做音频、不做记谱渲染、不做微分音 |

> 特别值得注意的一句定位（原文）：**"Every result on this page is a reading supported by evidence, not a fact recovered from the notes. A UI that presents one should show the supporting figures and allow an override."**
> —— "每个结果都是有依据的读法，不是从音符里还原的事实；界面应当展示支撑数据并允许用户覆盖。"
> 这跟我们《结果契约与展示设计》里定的"证据可见 + 用户可纠正"是同一个判断，说明这个方向没走偏。

### 1.1 它的做法（逐项）

**和弦识别**：`Chord.detectBest(音高数组)` / `detectMatches`（带依据）
- 返回的匹配结果带 `missingPcs`（缺的音）、`extraPcs`（多的音）、`exact`（是否精确）、`inversion`（转位）
- 细节设计好：**无法命名转位时 `inversion` 返回 `null`，但 `bassPc` 仍报出低音**——承认"知道低音是谁，但叫不出转位名"

**调性识别**：`Key.detectBest` / `detectMatches`
- 拿音级分布与每个候选调的"轮廓"做**皮尔逊相关**
- 轮廓可选：`krumhansl`（默认）、`temperley`、`flat`
- **把两个量分开报**：`fit`（调内音覆盖比例）与 `score`（相关系数，用于排序）
- 原文点破了关键："score 衡量权重落在哪些级上，**这正是区分一个调与它的关系调的东西**"
- `explain: true` 会给每个候选附理由，并且**给第一名列出它击败了谁、为什么输**
- 权重用"时值 × 力度"，并且专门说明"没有力度的音按满权重计，不按假定的值"

**时间轴与分段**：`Timeline.fromNotes` —— 这一节最值得抄
- 原文："**边界是搜出来的，不是照小节线切的**，所以一小节里两个和弦会得到两段"
- `segmentation` 两种模式：`'dynamic'`（默认，搜音符隐含的变化）/ `'grid'`（按固定拍数切，并注明"只在和声节奏确定不变时才对"）
- `harmonicRhythm` 是**搜索的先验**："和弦预期持续越久，放置一个变化所需的证据就越多"
- 静音处理很讲究：`dynamic` 下**长度达到先验拍数的静音不产生段**（查询返回空），更短的休止则并入周围和弦
- 硬门槛：**一个窗口凑不出任何和弦的两个音，就不产生段**

**置信度**（`segmentConfidence`）
> "置信度 = 该窗口里，被选中和弦自己的和弦音所承载的权重 / 该窗口总权重，匹配不精确时打折。
> 一个只有该和弦音的窗口读数为 1，而一个经过音的加入会把它拉低。"

**增六和弦**：单独一条路径
- 理由："没有任何三度堆叠的匹配能表达它"
- 判据：同一组音在降六级上**向外解决到属**（直接到 V / V7，或经过终止四六落在属低音上）→ 报增六和弦；
  解决到别处 → 退回 ♭VI7 的三度读法
- **这就是"按去向定功能"，不是按音集定名字**

**终止式**：六类 `authentic / plagal / half / deceptive / phrygian / modal`
- 完全 / 不完全：由**最高声部落点**决定（需要声部信息）
- 反复的 V 不算终止
- 终止式按"调实际拥有的级数"判断，不是固定半音距离（调式要特殊处理）
- **终止四六当作属和弦，不是转位主和弦**（观点很专业）

**简化（reduce）**：把和弦标成 `structural / passing / neighbor`
- 这正是"过滤经过和弦"的机制，也是我们 `Damascus` 出 90 段这个问题的解法
- 需要调性；两种基准：`'function'`（保留主、属、造成终止的）/ `'duration'`（比其他和弦长的，严格与其余和弦时长的中位数比）
- **从不降级进行开头和结尾的和弦**

### 1.2 与我们现状的对照

| 环节 | 我们（第二版） | libcantus | 差距 |
| --- | --- | --- | --- |
| 和弦识别 | 基础三/七和弦 + 折叠 | 完整匹配 + 缺音/多音/转位字段 | 他们更细；我们够用 |
| 调性 | 全局解码代价 + 音级分布互校 | 皮尔逊相关 + 轮廓可选 + 分离 fit 与 score | **我们排序口径不如人家清楚** |
| 分段 | 固定 1/16 网格 + 动态规划 | 动态搜索 + 和声节奏先验 | **我们网格是死的，他们是搜的** |
| 置信度 | 拍位差映射 + 调性方差分 | 和弦音权重占比（有明确定义） | **我们的是间接指标** |
| 经过和弦 | 无（只能靠转移代价抑制） | `reduce()` 标 passing/neighbor | **我们缺这一层** |
| 增六 | 无 | 单独路径，看解决方向 | **我们缺** |
| 终止式 | 现有 5 类（正格/变格/阻碍/半终止/ii-V-I） | 6 类 + 完全/不完全 | 接近，我们缺 phrygian/modal |

### 1.3 可以直接抄的五条（按性价比排序）

1. **分段改成"搜索"而不是"网格"**：`harmonicRhythm` 当先验——先估计"这里的和弦大概多久换一次"，再决定变换需要多少证据。
   这能同时解决我们的两个毛病：琶音被切碎、长 pad 被切碎。
2. **置信度改成"和弦音权重占比"**：这个定义简单、可解释、不受小节长度影响，比我们现在的"代价差映射"好解释得多。
3. **加一层 `reduce`（结构化 / 经过 / 辅助）**：把经过和弦从"和弦进行"里摘出去，是展平 90 段的正道。
4. **增六按解决方向判**（而不是按音集）：这正是我们"语汇层"缺的那一类，而且实现成本很低——只需要看下一段的根音是不是属。
5. **和弦定义外置成数据文件**（我们 55 个模板是硬编码在代码里的）。

## 二、midiharmony —— 另一条路：数据驱动的"和声质量"评估

| 项 | 内容 |
| --- | --- |
| 地址 | [asigalov61/midiharmony](https://github.com/asigalov61/midiharmony)（PyPI 同名包） |
| 做法 | 从 MIDI 提取和弦 → 分组 → 取连续"四和弦组合"（原文叫 quads）→ 与内置数据库比对 → 算 `harmony_ratio` |
| 输出 | 和弦总数、坏和弦数、四和弦组合数、唯一组合数、"和谐的四和弦组合"数、和谐比 |
| 用途 | 批量筛 MIDI 库（找出和声好/坏的曲子）、给音乐 AI 流水线做质检 |

**评价**：它**不做**调性判定、**不做**和弦进行输出，只回答"这个 MIDI 的和声像不像话"。
但它有两个想法可以借：
- **把"连续几个和弦的组合"当特征**（quad ≈ 我们所谓的"走向片段"），比只看单个和弦更能反映"和声是否成立"；
- **`harmony_ratio` 这种单值指标**很适合做批量筛选和回归测试的汇总指标。

**它给我们的启示**：如果以后要"批量扫我的采样库、挑出和声性强的 loop"，这条路（对比和弦组合库）比逐个精确分析更快、更宽容。

## 三、midi-chord-detector —— 实时输入 + 可视化

| 项 | 内容 |
| --- | --- |
| 地址 | [LongKelvin/midi-chord-detector](https://github.com/LongKelvin/midi-chord-detector) |
| 做法 | Python + PyQt6，接实时 MIDI 设备；核心是"和弦定义放 JSON 文件"（`chord_definitions.json`）+ 打分；界面显示 名称/根音/低音/类型/转位/分数 |
| 与我们的关系 | 相当于我们 `chord.rs` 的**交互版**：同样是模板匹配 + 打分 + 多字段输出 |

**可借鉴**：和弦定义外置成 JSON，用户能自己加和弦类型。我们现在 55 个模板写死在 `chord.rs` 里，
将来如果要支持用户自定义（或者从别的记法体系导入），这一步迟早要做。

## 五、为什么这些都不够——采样包 loop 的空白点

现成项目都假设了"完整作品"或"实时演奏"，而采样包 loop 的特点是：

| 特点 | 现成项目为何覆盖不到 |
| --- | --- |
| 只有 2–8 小节 | 统计类方法（皮尔逊相关、数据库比对）证据量不够 |
| 是循环片段 | 首尾不一定是主和弦，终止感不可靠 |
| 常缺声部（只有旋律或只有贝斯） | 它们默认有多声部输入 |
| 文件名自带调性 | 没人利用这个先验 |
| 常常没有速度事件 | 它们大多默认速度可信 |
| 大量是"分轨导出"（一条轨一个角色） | 它们按乐谱声部组织，不处理"多轨同通道" |

**结论：这块没有现成的轮子，得自己造。但造的时候可以少走弯路——分段、置信度、简化这三层直接照 `libcantus` 的思路做。**

| 优先级 | 事项 | 来源 |
