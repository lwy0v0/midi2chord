## 一、对外输出长什么样

### 音符级标注为什么必须有

只给"和弦名 + 和弦音集合"是不够的——**集合是合并过的音高类，看不出时间和八度**。
真正能判断"检测对不对"的，是逐音符的标注。

实际输出示例（`Cymatics - Lofi MIDI 1` 第一段）：

```text
1.1  Cmaj7   4.00 拍   根=C 低音=C
    音符：C3-根音(3.10)  C4-根音(2.86)  E4-三音(2.86)  G4-五音(2.80)  B4-七音(2.74)
          B5-七音(0.94)  E5-三音(1.90)  G5-旋律(0.13)  F2-延伸音(4.08)
```

一眼能看出的信息：

| 现象 | 说明 |
| --- | --- |
| `G5-旋律(0.13)` | 时值 0.13 拍、不在和弦里 → 判为旋律，**正确** |
| `E5-三音(1.90)` | 音高类 E 属于 Cmaj7，所以标成三音——但它其实是高八度的旋律线。**这是音高类判定的固有局限**，正是要暴露给人看 |
| `F2-延伸音(4.08)` | 低音 F 从第 4 拍起、属于下一个和弦，被归到了本段（段边界半拍误差）。**暴露的是分段问题** |

> 这三个例子说明：音符级标注的价值不在于"更准"，而在于**让错的地方显形**。
> 可视化时按 `角色标识` 上色（根=深蓝、三=蓝、五=青、七=紫、延伸=橙、旋律=灰），
> 一屏就能看出哪里涂错了。

### 三个必须坚持的设计

**① 调性允许有两个答案。**
短 loop 的关系大小调本来就分不清。强行二选一的后果是"十次里错三次，用户就不信了"。
正确做法：差距小时给"主判定 + 次判定"，并明确标出"模糊"。

**② 和弦给两套名字。**
`折叠名` 给人看（`C`），`精确名` 给核对（`Cmaj9/D`）。
只有一套名字时：给精确名，用户看不懂；给折叠名，出错了没法查。两套都给，各司其职。

**③ 排除音必须可见。**
每段都列出"哪些音被判定为和弦音、哪些被排除了"。
如果没有这个，用户看到结果不对时无从判断是算法错了还是素材本身就怪——而这是回归调试的唯一线索。

## 二、界面怎么摆

一共四个区块，从上到下：

### 区块 1：文件信息条

```
Cymatics - Lofi MIDI 1 - C Maj.mid    ·    4/4    ·    4 小节    ·    120 拍/分（文件未写，用默认）
```

### 区块 2：调性

```
        C 大调  ·  82%
        也有可能是 A 小调  ·  70%   ⓘ 这条 loop 是模糊的
```

- 主判定用大字
- 模糊时下方小字给次判定，带一个可展开的说明
- 点击展开"依据"列表

### 区块 3：时间轴（核心）

一条横向时间轴，按小节画刻度，每个和弦段一块色块：

```
1        2        3        4
├────────┼────────┼────────┼────────┤
│   C    │   F    │   C    │  F  │Dm│
│   I    │  IV    │   I    │ IV  │ii│
```

- 块上写 `折叠名`，下方小字写罗马数字
- 鼠标悬停显示 `精确名` + 置信度
- 置信度低的块用虚线边框或浅色，一眼能看出"这段不太确定"
- 半拍换和弦的块宽度按比例画——这就是"和声节奏"的视觉表现

### 区块 4：段落表 + 警告

表格列：`位置 | 长度 | 和弦 | 低音 | 置信度 | 证据`。
点"证据"展开该段的音符明细（哪些是和弦音，哪些被排除）。

警告区列出：缺速度事件、调性模糊、单声部、有未关闭的音符等。

## 三、用户能不能改（这是兜底）

**能，而且必须能。**

理由：调性和分段是当前最大的两个风险（见可行性分析 R1、R2），算法不可能全对。
如果用户不能改，一个错的结果就是死路；能改，错的就变成"可修正的初稿"。

允许的修改：

| 操作 | 效果 |
| --- | --- |
| 点某一段，从下拉里换一个和弦 | 该段更新 |
| 拖动段边界 | 和声节奏更新 |
| 删掉某段、合并相邻两段 | 同上 |
| 改调性（从 24 个里选） | 所有罗马数字重算 |
| 标记"这段听不出" | 该段标为 `?`，不参与统计 |

**不做的事**：不记忆用户的修改（没有学习功能）。
原因：修改是本次的临时修正，记下来会掩盖算法问题，也让结果不可复现。

## 四、界面上不要出现的东西

| 不显示 | 原因 |
| --- | --- |
| 音级集合、音程向量 | 调试信息，放日志里 |
| 每段的所有原始音符编号 | 太多，点开"证据"看概要就够 |
| 分值/权重这类内部数字 | 只给 0–100 的置信度，不给打分公式 |
| 英文缩写（PPQ、SMF 等） | 要用中文说"时间精度"，括号里保留缩写即可 |

> 这条是硬要求：**结果页上不该出现需要查资料才看得懂的词。**

## 五、先不做的事（避免范围膨胀）

| 项 | 说明 |
| --- | --- |
| 钢琴卷帘编辑器 | 是另一个产品 |
| 音频播放 / 试听段落 | 有用，但需要音频渲染链路，放到后面 |

| 和弦替换建议 / 转调建议 | 同上 |
| 批量分析整个文件夹 | 后面会很有用，但不是第一版 |
| 自动学习用户纠正 | 见第三节 |

## 六、和现有模块的接法

| 现有 | 复用方式 |
| --- | --- |
| `chord.rs` 的 55 个模板 | 不直接用。提取层要的是"折叠后的基础和弦"，单独的判据更简单也更稳 |
| `key.rs` 的 24 个调 | **直接用**（音级分布判据、按调号拼写） |
| `progression.rs` 的罗马数字 | **直接用**（把折叠和弦包成 `Chord` 喂进去） |
| `scoring.rs` 的 24 调打分 | **直接用**（把段序列喂进去），但需要和"音级分布判据"互相校验 |
| `analysis.rs` 的对外契约 | **不动**。MIDI 提取是新增命令，键盘输入走原来那条路 |

新增命令建议（名字待定）：

```
分析MIDI(文件字节) -> 上面的结果对象
```

文件怎么进后端：前端选文件 → 读成字节数组 → 调命令。这样不用加文件系统插件，也不用改权限配置。
